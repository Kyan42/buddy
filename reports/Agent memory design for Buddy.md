# Buddy should remember in plain files

As of November 2026, the state of the art in agent memory is a small curated text file loaded into every session, detail files read only on demand, and a consolidation pass that runs outside the conversation. Anthropic stores memory as files on every surface and documents exactly this loaded-index shape for Claude Code, and OpenAI's developer guidance and Google's newest "memory profiles" lean the same way. In the same-model comparisons available, plain full context matches or beats the commercial memory products at small scale; the loaded-file design itself has no independent benchmark. The unsolved problems are deciding what to write, replacing facts that have changed, and keeping injected content out of memory. Buddy should therefore load memory with the Claude Code file memory it already supports, and write memory through an inline tag that the app turns into a dated line, so that neither reading nor writing costs a tool call. In the first version the always-loaded index is the whole memory, and a consolidation run outside the voice process keeps it short. There is no documented sync between Claude Code memory and the Claude account memory used by Chat and Cowork, and The Register reported in August 2026 that Anthropic is keeping the two separate. The legitimate bridges are manual copies and file hand-offs built from official features, and none was tested end to end in this research. Vendor benchmark numbers below are labelled as self-reports, and every design step that rests on inference rather than documentation or a test is marked.

## The labs converged on a small loaded file plus detail on demand

**Every Anthropic memory surface is plain files.** The API memory tool is a client-side directory the model views, creates and edits ([memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). Claude Code keeps a `MEMORY.md` index plus one topic file per memory, typed as user, feedback, project or reference; it loads **only the first 200 lines or 25KB of the index** at session start and reads topic files on demand ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). Since 25 August 2026 the consumer memory in claude.ai is a list of short per-topic files that Claude writes during the chat, shared between Chat and cloud Cowork and editable by the user; it replaced a summary regenerated every 24 hours ([Anthropic, 25 Aug 2026](https://claude.com/blog/claudes-memory-works-everywhere-and-you-decide-whats-in-it); [help article](https://support.claude.com/en/articles/11817273-how-does-claude-s-memory-work)). Anthropic's newest statement, a 6 November 2026 post, describes four layers: transcripts, memory notes, memory representations such as a wiki, and injected context. Its advice is to keep the injected layer small, because it costs tokens every session and a wrong note is carried into every session ([The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)). Anthropic's stated reasons for files are spread over three pages: agents work best when memory builds on tools they already use ([Managed Agents memory](https://claude.com/blog/claude-managed-agents-memory)), just-in-time reads avoid stale indexes ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)), and people can see and correct what is remembered ([Anthropic, 25 Aug 2026](https://claude.com/blog/claudes-memory-works-everywhere-and-you-decide-whats-in-it)). How claude.ai brings its topic files into context is not documented. Anthropic has not published a head-to-head comparison of files against vector stores for memory; the case for files is assembled from those three points.

**The other labs split between the same shape and an opaque one.** OpenAI's Agents SDK writes `memory_summary.md` and `MEMORY.md` in a two-phase pass when a session closes and injects only the summary ([Agents SDK sandbox memory](https://openai.github.io/openai-agents-python/sandbox/memory/)). Its cookbook argues for a structured profile plus notes in the system prompt over retrieval, calls that placement very effective for latency, and says not every agent needs long-term memory on day one ([Context Engineering for Personalization](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization)). ChatGPT itself is the outlier: its "improved memory" is a continually updated synthesis whose mechanism OpenAI does not publish, and the summary shown to users is explicitly partial ([Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)). Google is the lab most committed to embeddings. Memory Bank stores independent facts per scope, written by an asynchronous extraction and consolidation pass and read back all at once or by similarity search ([Memory Bank](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank)). Yet its newest addition is fixed-schema profiles, justified as low-latency access with no search during the session ([Memory Profiles](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank/profiles)). Microsoft's Copilot Studio agents keep each user's memory as files in a per-user folder and delete it after 28 days without interaction ([Copilot Studio memory](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/memory-overview)), and Meta's Muse exposes an editable `Memory.md` ([Muse help page](https://www.meta.com/help/superintelligence/2225571704857152/)). Neither documents how those files are written or loaded. No lab in this set documents a knowledge graph as the memory of a shipped assistant; that is an absence across the pages read, not a claim any lab makes.

**The live disagreement is when to write.** Claude.ai, Claude Code and Google's memory-as-a-tool write inline during the conversation; Google's `GenerateMemories`, OpenAI's sandbox memory and Anthropic's Dreams API (a research-preview job that reads a memory store plus up to 100 past transcripts and writes a reorganized store) write in the background ([Create a Dream](https://platform.claude.com/docs/en/api/beta/dreams/create)). Anthropic states the trade directly: inline writes cost attention on the main task, and background passes do not interrupt but are not immediately available ([components post](https://www.anthropic.com/research/components-of-agent-memory)). The same post reports, as lab self-reported internal results, that frontier models do better with simple guidance (write a note when asked or when something clearly matters) than with fixed rules, that a newer model given filesystem memory wrote 10 files where an older one wrote 413, and that concurrent writers overwrote a shared page until it was split per entity. Practitioners point the same way. Andrej Karpathy's April 2026 "LLM Wiki" pattern has the model maintain a markdown wiki with an index file read first, and he reports the index working to roughly 100 sources and hundreds of pages without embedding infrastructure ([LLM Wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). Harrison Chase argues files are the right substrate but notes that wiki-style memory is a poor fit for user preferences and conversation state ([Wiki Memory](https://www.langchain.com/blog/wiki-memory)). That is the slice the labs handle with a small profile, not a wiki. Lilian Weng's vector-store framing of long-term memory dates from 2023 and is the view practice has moved away from ([Weng, 2023](https://lilianweng.github.io/posts/2023-06-23-agent/)).

## At one user's scale, simple baselines match the specialised systems

The academic vocabulary is settled: CoALA's working, episodic, semantic and procedural stores ([CoALA](https://arxiv.org/abs/2309.02427)), and a formation, evolution and retrieval lifecycle in the December 2025 survey ([Memory in the Age of AI Agents](https://arxiv.org/abs/2512.13564v2)). The designs are not settled, and the benchmarks used to rank them are weak. LoCoMo conversations fit in a modern context window. An April 2026 audit by Penfield Labs found a **6.4% wrong answer key** and a judge that accepted 62.81% of deliberately wrong on-topic answers; it is not peer reviewed, and its authors reportedly work on a competing memory project ([Penfield audit](https://penfieldlabs.substack.com/p/we-audited-locomo-64-of-the-answer)). Headline scores of 92 to 96% on LoCoMo or LongMemEval are **vendor self-reports** with undisclosed or differing answer models. Mastra's own table shows its unchanged memory layer moving from 84.23% to 94.87% on LongMemEval-S when the answer model changes from gpt-4o to gpt-5-mini, so these leaderboards mostly measure the answer model ([Mastra, vendor self-report](https://mastra.ai/research/observational-memory)).

**Where the comparison is fair, plain full context beats the commercial memory layers at small scale.** Mem0's own paper, a vendor self-report whose result runs against the vendor's interest, has full context at 72.90% on LoCoMo with GPT-4o-mini, ahead of Mem0's graph variant (68.44%), Mem0 (66.88%) and Zep (65.99%) ([Mem0 paper](https://arxiv.org/html/2504.19413)). A University of Illinois group with no stake in those products reproduced the ordering (full context 0.723; Mem0 0.613; Zep 0.585; LangMem 0.513), though their own lightweight retrieval method, EMem, scored higher at 0.780 ([Zhou and Han](https://arxiv.org/html/2511.17208)). A second Illinois paper found long context ahead of Mem0 and A-Mem with a 2026 model, again alongside a method of the authors' own ([StateMem paper](https://arxiv.org/html/2608.19652)). Letta reports, as a vendor, that an agent with file search tools over the raw LoCoMo history scored 74.0% ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory)). On MemoryAgentBench (ICLR 2026) the only like-for-like result is that plain BM25 (60.5 on accurate retrieval) beat the memory products (28.3 to 47.5) on the same backbone model; the long-context entries at the top of that table ran on stronger models ([MemoryAgentBench](https://arxiv.org/html/2507.05257v3)). On the independent MemoryArena benchmark, memory agents (0.12 to 0.14 task success) did not beat long-context models (0.16 to 0.19) or plain embedding retrieval (0.20) ([MemoryArena](https://arxiv.org/html/2602.16313)). The evidence does not show that simple designs beat all retrieval. It shows that the graph and multi-store products lose to simple baselines, and that the retrieval methods that win are themselves simple.

**Retrieval earns its place once history passes roughly 100k tokens, a size Buddy's curated memory will not reach soon.** In the LongMemEval paper, GPT-4o reading the full 115k-token history scored 0.606 against 0.870 when handed only the relevant sessions ([LongMemEval](https://arxiv.org/html/2410.10813v2)). Chroma, which sells a vector database, found focused prompts beating full prompts for all 18 models it tested ([Context Rot](https://www.trychroma.com/research/context-rot)). The latency figures are vendor measurements on 2024-2025 models with no statement about prompt caching: Mem0 measured a 9.87 s median for GPT-4o-mini reading 26k tokens against 0.71 s for its own retrieval path ([Mem0 paper](https://arxiv.org/html/2504.19413)). **No source measured time to first token for any memory design**, the metric Buddy cares about. The inference for Buddy is that a few thousand tokens loaded once at process start adds no round trip, and that each on-demand search adds a full model turn, so search belongs to explicit recall questions only.

**Written lessons improve agents, but only with a reliable signal.** Reflexion, Agent Workflow Memory, Dynamic Cheatsheet, ACE and ReasoningBank all show peer-reviewed gains from storing short lessons and re-reading them, with no weight updates ([ACE, ICLR 2026](https://arxiv.org/html/2510.04618v2); [ReasoningBank, ICLR 2026](https://arxiv.org/html/2509.25140)). All of that evidence comes from task benchmarks with a clear success signal, and ACE's own results fall when feedback is unreliable. A voice assistant has one dependable signal, an explicit correction from the user, so behaviour notes should be written from corrections and not from the assistant's own guess about what went well. That last step is an inference; no study measures procedural memory for a conversational assistant over weeks.

## The unsolved parts are writing, staleness and poisoning

**Extraction pipelines lose most of what they read.** HaluMem, whose authors are affiliated with one of the systems tested, measured memory-extraction recall of about 43% for Mem0 and update-omission rates of 52 to 94% for most of the systems tested ([HaluMem](https://arxiv.org/html/2511.03506v3)). LongMemEval's ablations show that replacing raw exchanges with extracted facts lowers accuracy, while using facts as extra index keys that point at the raw text raises it by 5.4% on average ([LongMemEval](https://arxiv.org/html/2410.10813v2)). Changed facts are worse still. On StateMemBench, long context, retrieval, Mem0 and GraphRAG all scored at or below 0.224 on whether an answer reflects the current state rather than a superseded one; the authors' own method scored best ([StateMemBench](https://arxiv.org/html/2608.19652)). On MemoryAgentBench the best selective-forgetting score was 32.5 ([MemoryAgentBench](https://arxiv.org/html/2507.05257v3)). Memory also gets applied where it does not belong: OP-Bench (EMNLP 2026) reports that over-personalisation is widespread once memory is introduced ([OP-Bench](https://arxiv.org/abs/2601.13722)). One write operation has direct evidence of catastrophic loss. When ACE let a model rewrite its whole memory in one step, the memory **collapsed from 18,282 tokens to 122** and accuracy fell below the no-memory baseline; the fix was itemized entries edited one at a time and merged by ordinary code ([ACE](https://arxiv.org/html/2510.04618v2)).

**Persistent memory turns a one-off prompt injection into a standing one.** Johann Rehberger showed in 2024 that a web page or document could make ChatGPT store attacker instructions that persisted across sessions; OpenAI closed the exfiltration channel but, by his account, not the ability of untrusted content to trigger a memory write ([Embrace The Red](https://embracethered.com/blog/posts/2024/chatgpt-macos-app-persistent-data-exfiltration/)). A 2026 study listed at ICML had documents and web pages induce assistants to store fabricated memories about the user. When the model wrote memory itself through a tool, the authors' optimised attack succeeded 99.8% of the time on GPT-5.5 and 64.2% on Claude Sonnet 4.6 (on the study's behaviour subset). With a separate memory manager deciding what to store, Sonnet 4.6 fell to 13.6%, yet 24 of 25 manual attempts against the Claude production app still stored the memory. Prompt-level defences were inconsistent across models ([sleeper memory study](https://arxiv.org/html/2605.15338)). A Huawei Canada study of two open-source agents found one markedly easier to poison (66.67% attack success against 34.25%). The authors attribute the difference to its more permissive writes and to its injecting persistent memory into the system prompt at session start, where the other agent retrieves memory only on a tool call ([MPBench study](https://arxiv.org/html/2606.04329)). Loading at session start is the configuration Buddy wants for latency, which moves the burden onto the write side. The recurring recommendations are tight write policies, treating external content differently from authenticated user input, provenance on every entry, and memory the user can see and delete. No reviewed study measured user review or confirm-before-write as a defence, so their value here is a design inference.

## Buddy's first memory is one index the app writes

The design follows from two facts established by the project's own tests. Loading is free: with `autoMemoryDirectory` set, the CLI puts the `MEMORY.md` index in context at process start with no tool call, and the process restarts at least every 8 turns. Writing and topic-file reads are not free: the CLI does both with file tools, and a tool call delays the rest of a spoken reply by 5 to 10 seconds. Anthropic's SDK documentation confirms that auto memory is saved with the standard Write and Edit tools, so a process without them loads memory but cannot save it ([Agent SDK features](https://code.claude.com/docs/en/agent-sdk/claude-code-features)). The recommendation is therefore to keep the built-in mechanism for loading and to move writing into the app, using the inline-tag pattern Buddy already uses for pen marks and `read_session`. An inline tag is the primary write path rather than a background extraction pass for three reasons. It needs no second model run. It matches how claude.ai and Claude Code now write, during the conversation. And extraction pipelines are where the measured omission and error rates are worst.

| Aspect | Recommendation for version one | Basis |
|---|---|---|
| What is stored | Three kinds of entry: stable facts about the user, how the user wants Buddy to behave (written only from explicit corrections or requests), and ongoing work that neither the screen nor the Claude Code session list shows. Nothing derivable from the screenshot or session list. | Mirrors Claude Code's user, feedback and project types (documented); corrections-only rule is an inference from ACE and CoALA |
| Form | One folder used only by Buddy (for example `~/.claude/buddy-memory/`). `MEMORY.md` holds the entries themselves, one line each, grouped under three headings, each line carrying a date, a provenance mark and a short ID, for example `- [2026-11-10] [said] m-0012 Prefers answers under three sentences`. Because Buddy cannot open topic files without a tool call, each index line is the fact, not a pointer. An `archive.md` receives replaced lines, and an append-only `memory-log.jsonl` records each write with the interaction ID and the user's transcribed words. | File name, folder mechanism and 200-line / 25KB cap documented. The line format is a deliberate departure: Claude Code's documented index holds one pointer line per memory, linking to a topic file with a typed header. Facts-in-index is a design inference |
| How it is written | Buddy writes `<remember section="...">text</remember>`, `<remember replaces="m-0012">text</remember>` or `<forget id="m-0012"/>` inline in its reply. The app strips the tag from speech, as it does for marks, and applies it as a single-line edit. The prompt guidance stays simple: save when the user asks, or when something the user said clearly matters later. Buddy says a few words when it saves, so every write is audible. | Tag pattern tested in Buddy for other tags; applying it to memory is untested |
| How it is loaded | `autoMemoryDirectory` passed to Buddy's CLI process through its own settings, so the index is in context at process start with no tool call. New entries are already in the running conversation and reach the loaded index at the next restart. Detail beyond the index comes later through a `read_memory` tag that works like `read_session`. | Loading tested; `--settings` scope documented; pickup of app-written lines at restart is inferred and untested |
| How it is consolidated | When the index passes about 120 lines, or on request from the panel, a separate one-shot Claude Code run outside the voice process, with file tools limited to the memory folder, merges duplicates, drops superseded lines and shortens entries by line-level edits. The run is instructed to add no facts that were not already present. The app cannot enforce that instruction in code, so it snapshots the folder first (a git commit or a dated copy), rejects a result that shrinks the file sharply, and keeps the diff for review. | Pattern documented by Anthropic, OpenAI and Google; thresholds are placeholders; untested |
| Guards | Entries come only from what the user said, never from screenshot content, the session list or `read_session` content. Anything from another source, including the account memory and notes left by Chat or Cowork, enters the index only after the user approves it, and carries its own provenance mark. The app, not the model, chooses the file path and enforces caps (one line, a length limit, a few writes per turn). Edits are itemized, never whole-file rewrites. Memory is advisory: the current request and screen win, and a memory is used only when it bears on the request. The file is plain text with an "Open memory" button in the panel. | Source rule and provenance from the security studies; path and size control from Anthropic's memory tool guidance; user review as a defence is an unmeasured inference |

**Buddy's always-loaded file should not be writable by desktop Claude Code sessions in version one.** Setting `autoMemoryDirectory` at user scope would make every session share one folder, and that is documented and takes one line ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). The cost is that coding sessions read repositories and web pages, and anything they save would be injected into every Buddy conversation with no retrieval step in the way, the configuration the Huawei study associates with easier poisoning. Anthropic's own account of concurrent writers overwriting a shared page is a second reason, and per-repository project notes would crowd a 200-line index a third. The safer way to make Buddy feel like an extension of Claude Code is one-directional. Buddy's folder uses Claude Code's file name, folder mechanism and size cap, with its own line format, and stays plain markdown that people and Claude Code can read. As an optional step, a new `~/.claude/CLAUDE.md` can import Buddy's index with an `@path` line, so every Claude Code session on the machine starts with what Buddy knows about the user; the import mechanism is documented, and this use is inferred and untested. The import has a cost. Buddy's writes rest on a prompt-level source rule with a screenshot in every turn, and the import sends each entry into sessions that have tools, so a bad entry travels further than Buddy. Buddy keeps reading Claude Code's side through the session list and `read_session`. Two things need checking before relying on the import: whether Buddy's own CLI process would also load that `CLAUDE.md` and so see the index twice, and whether Claude Code's built-in memory instructions make a tool-less Buddy talk about being unable to save.

Three limits of this design are known in advance. The source rule for writes is enforced by the prompt, and the sleeper-memory study shows prompt-level defences are inconsistent, so the code-level caps, the audible acknowledgement and the readable file carry real weight. Speech-recognition errors can be stored as facts, and no study covers that. And nothing published measures what a few thousand always-loaded tokens do to time to first token, so the first build should compare Buddy's own `msReleaseToFirstAudio` with and without the index.

### What to defer

Defer embeddings and any vector store, knowledge graphs, and retrieval over raw transcripts: the evidence for them begins around 100k tokens of history, far above a curated index. Defer automatic extraction of memories from transcripts, given the omission rates measured for extraction pipelines; Buddy's existing 30-day interaction log already preserves the raw record if that step is added later. Defer topic files and the `read_memory` tag until the index cannot hold what matters after consolidation. Defer lessons that Buddy infers by itself, time-based decay and expiry, a confirm-before-write interface, a shared writable folder with Claude Code, and any automatic sync with the account memory. The signals to revisit are an index that will not stay under the cap after consolidation, and recall questions the index repeatedly cannot answer.

## No sync exists, so the account memory is bridged with files

Claude Code memory and the account memory are separate systems with no documented link. Claude Code's auto memory is machine-local ([Claude Code memory docs](https://code.claude.com/docs/en/memory)), the August 2026 memory announcement does not mention Claude Code or any developer access, and The Register reported Anthropic saying Claude Code's memory stays separate, with nothing to share about its future; that is a press paraphrase, not a published Anthropic statement ([The Register, 25 Aug 2026](https://www.theregister.com/ai-and-ml/2026/08/25/claude-and-cowork-now-share-what-they-know-about-you/5292412)). What the two sides do share is connectors: those added in claude.ai load automatically into Claude Code under a subscription login ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)). The account memory can be read and written through official manual routes. Claude can be asked in chat to write out memory verbatim, to remember or forget something, and Settings has a paste-in importer that Anthropic labels experimental and that may not keep everything ([import and export article](https://support.claude.com/en/articles/12123587-import-and-export-your-memory-from-claude)). A skill file shipped with the desktop app on this Mac (`~/Library/Application Support/Claude/local-agent-mode-sessions/skills-plugin/<ids>/skills/import-memory/SKILL.md`) describes the importer's format as one dated fact per line under five categories, a 64KB cap, and roughly ten memory writes per turn. That is a local observation of undocumented internals and can change with any app update. It suggests one cheap alignment: Buddy's dated one-fact-per-line entries are already close to what the importer expects.

The table ranks the options by fit for a first version: official support first, then least new machinery and exposure, then reach. Each status uses three terms. Documented means an Anthropic page describes the feature, inferred means the use as a memory bridge follows from documented parts but is stated nowhere, and untested means nobody ran it end to end in this research. Under every legitimate route the two memories stay different, because the account side rewrites and filters what it stores and reads from it pass through the model. That too is an inference. The account memory is also not a trusted source for Buddy: the sleeper-memory study's 24 of 25 successful manual attempts were against the Claude app. So in every row below, text arriving from the account side lands in a file Buddy does not load, and reaches the index only through the approval rule in the design table.

| Rank | Option | Direction | Status | Note |
|---|---|---|---|---|
| 1 | Ask Claude in chat to write out all memory verbatim, and save the text as `claude_account_memory.md` in Buddy's folder, which Buddy does not load; lines the user approves go into the index marked `[account]` | Account to Buddy | Write-out documented; use as a Buddy source inferred; completeness of the dump untested | Manual; a snapshot that ages |
| 2 | Paste Buddy's entries into a chat and ask Claude to remember them, or edit Topics by hand in Settings | Buddy to account | Documented; applies from the next conversation | Manual; the model rewords and filters sensitive categories |
| 3 | Settings importer ("Start import") with Buddy's entries in the importer's own line format | Buddy to account | Feature documented; use for one's own notes inferred; untested | Experimental, additive, lossy; the cap is known only from the local skill file |
| 4 | Profile Instructions holding a short copy of Buddy's key facts | Buddy to every chat, as instructions, not memory | Documented; automatic once pasted | Manual to update; best for stable facts ([personalization article](https://support.claude.com/en/articles/10185728-understanding-claude-s-personalization-features)) |
| 5 | Connect Buddy's memory folder in the desktop app and give a dedicated "Buddy" Project instructions to read the index and append new facts to an `inbox.md` that Buddy does not auto-load | Both, on this Mac with the app open | Folder access documented; bridge use inferred; untested | The inbox keeps cloud sessions from writing into Buddy's loaded file, and inbox lines reach the index only on the user's approval; instructions are advice, not a trigger ([Cowork and chat article](https://support.claude.com/en/articles/16761823-claude-cowork-and-chat-are-one-claude)) |
| 6 | Scheduled Cowork task that refreshes `claude_account_memory.md` in the folder, or reads Buddy's entries and remembers them | Both | Parts documented; combination inferred; untested | Unknown whether scheduled runs read or write account memory on personal plans ([scheduling article](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork)) |
| 7 | Local Filesystem MCP server or desktop extension scoped to the folder | Chat reads and writes Buddy's files | Mechanism documented; availability in cloud-run chats untested | Two support articles conflict on local MCP in cloud sessions; adds nothing over option 5 |
| 8 | Google Drive connector folder as the shared store, synced locally | Both | Connector documented; pattern is a community kit; untested here | No in-place edits to a document, per the kit's author ([community kit](https://github.com/kuzubis/claude-shared-memory/blob/main/docs/how-it-works.md)) |
| 9 | Custom remote MCP memory connector | Every surface, including Buddy's CLI | Mechanism documented; memory use inferred; untested | Needs a public HTTPS endpoint with sign-in in front of private notes; the private tunnel is Enterprise only; for Buddy a connector is a tool call, with the 5 to 10 second stall ([remote connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)) |
| 10 | Account data export, parsing memory from the ZIP | Account to Buddy | Inclusion documented; memory format undocumented, third parties disagree | Manual request, emailed link |

Three routes are excluded. Tools that call claude.ai's private endpoints with the logged-in session are unofficial and carry terms-of-service risk. The Compliance API is Enterprise only. A built-in sync does not exist. Options 1 to 4 are worth doing now, because they cost minutes and touch nothing fragile. Options 5 and 6 are the ones worth a short experiment, and each hinges on a point the documentation leaves open. A third cheap check concerns Buddy alone. Because claude.ai connectors load into any Claude Code process on a subscription login, Buddy's warm process may already carry them, which is an inference worth confirming for its effect on context size and on which tools Buddy has.

## Conclusion

The field's direction and Buddy's constraints agree. The 2023 picture of agent memory as a vector store behind a retrieval call has given way, in what labs ship and in what holds up under independent testing, to model-maintained text that a person can read. A voice assistant that cannot afford a tool call lands on the most conservative corner of that pattern, and that corner is also where the evidence is strongest. What decides whether Buddy's memory is good is therefore the write policy: which sentences earn a line, who is allowed to cause a write, and how a changed fact replaces an old one. Those are choices about prompts and a few dozen lines of app code.

The account-memory question has a less satisfying answer, and the right response is to design around it. Anthropic has built two memories of the same shape, short markdown files on both sides, and by The Register's account is keeping them apart. Making Buddy's folder the source of truth and treating the account memory as a second, lossy audience for it costs almost nothing today. It also leaves Buddy's entries ready to move if an official bridge arrives, because they are already dated, single-fact and marked with where they came from.
